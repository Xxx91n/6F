# Spec: macro-audit spec 阶段展开

> 来源：架构报告 spec-phase-tasks.md 18 项（治理工件已退役，原文见 git 历史）
> 决策 ledger：decision-ledger.md A-001 ~ A-048（治理工件已退役，原文见 git 历史）

## 要解决的问题

宏观加微观的工程内容审计产品，前面那轮讨论已经把大方向定完了：7 条决定都算现行的，当时落了 7 份 ADR。这一轮要把话说到能干活的程度——S1–S5 这五个战略问题各自的判据全文、集成层的表结构和接口约定、报告模板里各档共用的那部分、10 条演示路径的具体内容。没有这份 spec，前面定的方向落不了地。

## 怎么做

把架构报告（spec-phase-tasks.md）里那 18 个卡点一条不落地登记成决策账本（A-001 ~ A-018），再按「战略判据 / 集成架构 / 报告模板 / 演示路径」四组展开成一条条决定。每条决定下面都写明它覆盖哪个 A 号；接着照依赖关系切成 18 张票、18 份交接单、18 份开工提示；哪些能同时跑，看票上的 Blocked by 字段推出来，结果写进 README.md。

## 用户故事

1. 我是这个审计产品的内部架构师：我要 S1–S5 这五个问题在五档审计下都各有具体判据、数据来源和阈值，这样每个真仓库都能跑出一份可重复的报告。
2. 我是负责落地「一张事实表、各处裁决」这套集成架构的人：我要 DuckDB 事实表的写入策略和表结构演进规则写明白，这样五档审计才能共用同一个事实底座。
3. 我是设计报告模板的人：我要五档 × 四个面的共用结构、以及各档自己那部分的边界写明白，这样跨仓叙事的 Macro-A 和按 PR 行级看的 Micro-A 能装进同一套模板。
4. 我是安排演示的人：我要 10 条演示路径（顺利路径和失败路径）各自的触发条件、降级方式、出什么报告都写明白，这样我才能交付能点开看的失败演示。
5. 我是维护这个仓库的人：我要每张票覆盖哪个 A 号一眼看得见，这样任意一条决定都能顺着号倒查回当初那个卡点。
6. 我是被派来做子任务的 agent：我要开工提示不超过 60 行、附必读清单和只跟本次相关的增量，这样我在一个全新的会话里也能直接开工，不必重复已知的规矩。

## 定下来的决定

每条决定都必须挂上至少一个 A 号。还没定去向的条目清单只要不是空的，就不许开票。

### 第一组：五个战略问题的判据全文

#### Decision 4.1 — S1 定位收敛怎么量
- 70% 这个数不当硬规矩卡死；交出来的东西是试点仓清单加一套校对流程（怎么挑 embedding、关键词怎么兜底、人工怎么抽检）
- 跟 4.5 那张矩阵对齐：每一行里「语义度量」那一格，照 4.5 的矩阵格式填
- **来源**：A-001

#### Decision 4.2 — S2 ADR 质量：怎么判是不是事后补写
- 交两份东西：一份核对清单，查被审仓的 ADR 头上那几行 YAML 时间戳对不对得上；一份是头缺了怎么办的退路
- 初版先用一个数：ADR 事后补写超过 90 天的那部分占比超过 20%，判失败；以后要跨仓校对，先留好位置
- **来源**：A-002

#### Decision 4.3 — S4 从 ADR 里把假设抽出来
- 这套工具必须是一边让模型抽、一边有人复核，只信模型不算数
- 交一张模板，把「当初的假设后来失效了」逐条列出来对照（参照 InfoQ 的 ADR Drift Monitor 那套想法清单）
- **来源**：A-003

#### Decision 4.4 — S5 单人仓这个面信号弱，怎么降权
- 按团队大小画一张归一化的曲线：一个模块被一个人写掉的比例，跟团队人数分档对应起来给阈值
- 报告模板里要写明白：信号不够的时候怎么退（按第一组这些判据的约束来）
- **来源**：A-004

#### Decision 4.5 — 25 格采集矩阵
- 矩阵是 5 个维 × 5 档 = 25 格；每一格都要写清四件事：这条判据怎么定义、数据从哪来、初版阈值多少、以后怎么跨仓校对
- 它是上面 4.1 到 4.4 更上一层的东西：任何只管一个维的决定，都得能填进矩阵里对应的那一行
- **来源**：A-005

#### Decision 4.6 — AI 写代码会不会把 ADR 质量带坏
- 先往后放，优先级低。这轮只交一个「将来怎么评」的框架：指标怎么定、样本怎么取；真去评估，等 AI 写代码成了主流再说
- **来源**：A-006

### 第二组：把「一张事实表、各处裁决」这套架构落地

#### Decision 5.1 — 事实写进 DuckDB 时谁来写
- 摆在面前的是两条路：一个写、多个读，还是多个写、多个读。选前者：事实只存一份，写由一个集中的写进程管
- 还要管两件事：并发怎么控（事务隔离级别定在哪一档）；版本怎么带（每条事件上都带版本号）
- **来源**：A-007

#### Decision 5.2 — 表结构以后怎么升级
- 照事件契约那套做法：已经发出去的结构不许就地改，要升级就加版本号，读的一方按版本订自己认识的那版
- 得有个地方查：哪个版本现在是在用的
- **来源**：A-008

#### Decision 5.3 — 读到的数据旧了怎么办
- 定一条容忍线：读出来的东西最多能旧 5 秒；投影跟不上这条线就报警
- 报告模板里那个「数据已陈旧」的标记字段要跟这条线对上
- **来源**：A-009

#### Decision 5.4 — 不同档之间靠什么对得上
- 事实表结构里，前面先留两个字段：trace_id 和 baggage_id（借 OpenTelemetry 里 Baggage 那个思路）
- 五档都用这两个字段，才能把同一个提交或同一个 PR 跨档对上
- **来源**：A-010

#### Decision 5.5 — 要不要上 LangGraph 当调度
- 两条路选一条：用 LangGraph，还是自己造一层负责协调的东西。评的结果做成一张对照表：跟本仓的语言栈合不合、上手要多久、跟「事实只存一份」的想法冲不冲突
- **来源**：A-011

#### Decision 5.6 — Data mesh 那三种翻车怎么防
- 三种翻车各配一道防线加一项监视指标：中间那段没人认领 / 悄悄断掉 / 两边重复干同一件事
- **来源**：A-012

#### Decision 5.7 — 外部工具跟本仓能不能对上
- 把指标层、OpenTelemetry baggage、AsyncAPI、LangGraph 这几样，逐个跟本仓的语言栈做一张契合度对照表
- **来源**：A-013

### 第三组：报告模板 = 共用结构 + 各档自己那部分

#### Decision 6.1 — 各档共用结构取什么最小公约数
- 在 5 档 × 4 个象限那张表上取交集，列出哪些字段两边都得有：章的先后顺序固定、字段必须有、措辞不固定
- **来源**：A-014

#### Decision 6.2 — 各档自己那部分差在哪
- 列清楚 Macro-A（跨仓叙事）、Micro-A（按 PR 看改动）和另外三档各差哪些字段
- 每一档自己那部分都要写五项：什么事件触发、吃什么输入、输出细到什么程度、引文写多密、判定印盖在哪
- **来源**：A-015

#### Decision 6.3 — 样式归谁管、结构归谁管
- 结构和字段由 spec 定死；长什么样、怎么排由演示那边定。这样 spec 不会越界去管界面
- **来源**：A-016

### 第四组：演示场景 = 10 条路径

#### Decision 7.1 — 每条路径值不值得做成能点的
- 十条路径逐条对比，做成一张表：这条要不要真能点开跑，还是写份文档说明就行（10 行 × 2 列）
- **来源**：A-017

#### Decision 7.2 — 五条失败路径各写成什么样
- 五条失败路径每条都要写四件事：什么条件下触发、退到哪一步、判定关拒绝时盖什么印、最后出什么样的报告
- **来源**：A-018

### R2-01 — 四类目标用户，一个不少

**不许做的事**：不许把范围缩成只有一类用户；也不给这几类人排优先级，更不按时间先后分批做（跟当初拒掉「砍出来的第一版」是同一个道理）。

#### A 类 —— 技术决策者（CTO / 架构师 / 尽调人）
- **什么时候用**：尽调或者架构拍板之前看一眼，就一次；要给外部仓库或一组仓库一个能倒查的判定。
- **拿到什么**：四象限叙事报告（结构 / 行为 / 供应链 / 战略），加证据引文，加 S1–S5 的战略诊断；不写代码的人也能读。
- **主要走哪档**：Macro-A / Macro-B（另外还有 Macro-C）。
- **拉着我们改进什么**：让不写代码的人也能读懂报告。

#### B 类 —— 工程团队（TL / 平台组 / 质量负责人）
- **什么时候用**：定期评审，或者 CI 关卡被触发的时候（push / PR 自动触发）。
- **拿到什么**：判定关的裁决，加按行带引文的评审，加误报少、能照着做的建议。
- **主要走哪档**：Micro-A / Macro-B。
- **拉着我们改进什么**：CI 关卡要稳、误报要少。

#### C 类 —— agent 生态开发者（Claude Code / Codex 用户）
- **什么时候用**：嵌在 agent 工作流里的时候，在会话里说一句「审一下这个仓库」。
- **拿到什么**：装一次就能用的 Agent 插件，加一个 MCP 只读证据查询面，加 Macro-B 的四象限叙事报告。
- **主要走哪档**：Macro-B，这也是默认模式。
- **拉着我们改进什么**：插件要能分发出去，MCP 接口要稳。

#### D 类 —— 自己用（本人加 jiahao / anysearch-cli / env-manager）
- **什么时候用**：想手动跑一遍的时候；也拿它当校对锚，帮我们把判据调准。
- **拿到什么**：本地能重复跑出来的审计报告，加一条拿真实反馈校对判据的回路。
- **主要走哪档**：Macro-B / Macro-C。
- **拉着我们改进什么**：本地必须能重复跑出来。

### R2-03 — 默认模式装完就能跑，得满足什么

**覆盖：默认模式装完就能跑 / Agent 插件那一组约定 / 收进来的东西按什么规则处理**

- **默认模式是啥**：C 类人嵌在 agent 工作流里跑的那一档，也就是 Macro-B，按仓库整体看四个面；装完不用配东西（不用配 CI、不用挂 hook、不用先跟团队打招呼）。
- **「不用配东西」到底指什么**：敲一次安装命令，加第一次给 MCP 工具授权；除了这两下，中间不用你再动手。
- **第一次要授权哪几件事**（一件一件列）：
  1. 装 Agent 插件（plugin.json + skills/ + mcp.json + 扩展目录 + 内核 CLI）；
  2. 第一次起内核 MCP（stdio）→ 客户端弹窗问你要不要授权用 MCP 工具；
  3. 第一次读本地仓库路径 → 要授权读本地文件；
  4. 输入是远程仓库时：「克隆下来 + 联网 + 用本机 git 凭据」算一件事，一次授权（这条的细则在输入面那节）；
  5. 第一次写 DuckDB 事实表或者缓存目录 → 要授权往本地写。
- **怎么验**：默认模式得跟分发渠道对得上（市场里一键装，装完直接能跑）；默认这一套不许非得配 CI 或者配 hook 才能跑通，不然跟「一键装」自相矛盾。
- **风险记一笔**：默认这套的前提是你得在 agent 会话里发起。宿主要是不支持插件这种形态，默认模式就用不上（哪些宿主支持这事等进实施阶段再查，这层只把前提说清楚）。

### R2-04 — Agent 插件那一组约定

**覆盖：Agent 插件那一组约定**

- **plugin.json**：按 Agent Plugins 1.0.0 这个标准写（结构是封闭的，`$schema` 是个固定 URI，客户端不许运行的时候再去拉结构定义）；里面有 name / version / description / skills / mcp / commands 这些字段（每个字段具体什么样，等把规范全文读完再定稿，见后面的信息缺口）。
- **mcp.json**：内核那个 MCP 面，只用来查证据；走 stdio 传输，指向 DuckDB 事实表；严格只读（跟 GitHub Copilot 代码评审那个 MCP 强制 `readOnlyHint` 是同一个规矩）。
- **两份清单从一个源头生成**：只有一份元数据源（比如 manifest.meta.json），由它生成标准 plugin.json 和 Claude Code 原生的 .claude-plugin/plugin.json；生成完再 diff 比一遍，防着两边跑偏；**这事没有现成先例可抄，得自己写**（调研见 R2-Q7 §3）。
- **内核 CLI 的四个外壳**：插件里嵌的、GitHub Action、自己用的 CLI、报告生成器——同一个二进制，四个入口。
- **回执里有哪些字段**：环境外的确定性关卡出一张能核验的回执，里面带证据引用、判定结果、能离线复核；报告里「行动建议」那一章盖的判定关印，就是它在报告这层的形态。
- **出处清单**：许可证、变更记录、签名（Sigstore / cosign keyless）、构建来源（参照 SLSA）。
- **安全上的规矩**：skill 那层只读且隔离，判定、写库、出报告都只能由内核 CLI 干；hooks 永远不当裁决的执行点，只在 PostToolUse / Stop 时触发或者把回执摆出来。

### R2-05 — 收进来的东西按什么规则处理

**覆盖：收进来的东西按什么规则处理**

- **repo add 这个命令**：repo add <path|owner/repo|url>；克隆只走 CLI 和配置文件，不暴露成 MCP 工具。
- **怎么认**：给的是明确的本地路径就用本地的；给的是 owner/repo 这种形状，先在本机找，找到了就用本地的，`./` 前缀表示一定按本地处理；只有给了明确 URL（https / git@）才去克隆。
- **克隆下来放哪**：放一个单独的缓存目录里（比如 <cache>/repos/<hash>/），不写回你自己的工作区，审完可以清掉。
- **凭据怎么用**：沿用本机 git 那套凭据链（SSH agent / credential helper / PAT，用完就清），不另建一个存凭据的地方。
- **历史不全就拒**：远程克隆一律 fetch-depth 0，再查 .git 是否完整；浅克隆明确拒绝并提示。
- **授权事件那几个字段**：见 R2-03 第一次授权清单里的第 4 条。

### R9-1 — `prereg_commit` 只取可解析 commit，或带前缀的明确标记

- **决策**：报告里的 `gate_ref.prereg_commit` 只允许三种值：① 一枚能真正解析的 commit（4–40 位小写十六进制；下限取 4，因为 git 能吐出的最短缩写就是 4 位，`core.abbrev` 小于 4 会被 git 忽略；而且必须真能解析成这个仓里的一个 commit，长得像但指错对象不算）；② 以 `sentinel:` 开头的存档哨兵（一个占位值，它本来就不是 commit）；③ 以 `degraded:` 开头的明确降级（本该取到 commit，但取不到或取不准）。三种以外的值一律不行，生成回执时当场退回，不让读者去猜。这条规矩管的是用户能看到的报告：读者不翻源码，也能判断这个坐标是不是 commit、能不能回头查。
- **为什么要定这条规矩**：这个字段以前混着三种值——真 commit、仓里没有定义的存档字面量、以及浅克隆时悄悄取到的边界 commit。第三种最麻烦：它看起来就是一枚合法 commit，不报错，还会随克隆深度变化，同一个判据件在两种克隆方式下给出不同的锚和不同的回执摘要。「取对了没有」这件事，读者在报告里查不出来，只能靠发出方用值本身的样子来证明。
- **拿不到历史时，不许悄悄糊弄**：取不到判据件最后一次改动的 commit 时，不要返回边界 commit，而是写一个带名字的降级标记。现在的清单一共五枚：`resolvePreregCommit` 产出四枚——`degraded:shallow-clone`（确认是浅克隆）、`degraded:no-source-repo`（安装态插件没有源码仓根）、`degraded:depth-unknown`（判不出克隆深度）、`degraded:no-criteria-history`（这个仓里取不到判据件的 commit）——另外契约生成脚本 `51-macro-b-behavior.mjs` 真实运行时会产出 `degraded:unanchored-run`。这五枚就是本条登记的清单：以后新增一枚，必须先把名字写在这里——`85-check` A17 只看写法对不对，看不出名字在不在册，只有写在这里才和代码对得上。是不是浅克隆，用 `git rev-parse --is-shallow-repository` 判断；`--filter=` 这类只取部分历史的克隆不在上面这份清单里，现在不判成降级（仍可能交出边界 commit），要不要把判断范围扩大另定。「全量历史属受支持运行形态」这条裁定，以及三份 workflow 里 `fetch-depth: 0` 的现状，都写在 `docs/adr/` 的现行架构决定里（索引见 [`docs/adr/README.md`](adr/README.md)），本条不抄一遍。降级能被机器查出来，不许用 SKIP 混过去（承 tracker #35 的规矩：被跳过的检查组不能当作没发生）。
- **两种标记的写法不可能撞在一起**：标记前缀里带冒号，git 短 SHA 和全 SHA 的字符里都没有冒号。这两种标记只能由专门的生成函数产出，直接写死的字面量不再算合法锚。短 SHA 显示几位（在 7 和 8 之间跳）只关乎宽度，不关乎身份；沿用 tracker #84 的全值比较规则，本条不再重复。commit 这种值的宽度下限取 **4**，不取 7：git 自己能吐出的最短缩写就是 4 位（`core.abbrev` 小于 4 会被 git 自己忽略）。如果门槛设在 7，`core.abbrev=4` 的检出就会交出一个「写法合法、却被门槛判成说不清」的锚，报告在组装时抛错、存不下来——这是判定规则自己造成的可用性问题。反过来，给取值加 `--abbrev=7` 也不干：它会把本仓自然的 8 位缩写固定成 7 位，改动的正是 tracker #86 明确排除的宽度表示方式，还会让 `48-micro-a-golden-*` 十二件和生成器对不上。
- **这条规矩只管对外发出的内容，不改历史现场**：`38-*` 冻结件、`51-macro-b-*` 和 `23-first-report` 存档件里原来那种不带前缀的写法（连同各自已经算好的回执链）一个字节都不动——按 [`docs/authority.md`](authority.md) §3 的历史编号规则，按字节冻住的历史存档可以保留原样。对外发出的内容改成带标记的写法以后，存档里的那一枚仍按「历史编号」读。同一个名字两种写法并存，不算有两套现行说法：现行规则只有本条这一种，另一枚是已经声明为历史产物的出处坐标。
- **和 D-179① 的关系**：D-179①（历史编号，这里只作引用）定了一条「伴生确定性」：判据件跟着它最后一次改动的 commit 固定下来，取值就取这个 commit；这个含义在浅克隆下会悄悄失准，本条补的是**取不到真值时该写成什么样**，不改它的取值定义。
