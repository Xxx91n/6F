# ADR-0029: 放宽「机器读的名字不许改」这条规矩

- Status: accepted
- Date: 2026-11-12
- Supersedes: 无
- 来由：tracker #212 提的四条取舍。tracker #231 由用户点头接受，本文件从此是现行决定。
- 同批文档面改动：`docs/spec.md` §R10-3（禁令那句收窄成「出仓的机器读名字一律不动」，并加指向本文件的链接）、§R10-5 与 §R10-7 改成指向本文件、R10 覆盖表一行；`docs/authority.md` 顶段、§2 表里 `engine/test/fixtures/contracts/` 那一行、§4 那条；`docs/adr/0028` 的入口那句。判据写在本文第 1、2 条；spec 那三处留的是禁令本身和一句话指针，不重复判据。

## Context

在 tracker #231 之前，仓里有一条不留余地的硬规矩：机器读的名字不许改。正文在 `docs/spec.md` §R10-3，列的是「命令、参数、错误码、JSON 键、数据库列、环境变量、文件路径、`preview_disclosure` 这类字段」；§R10-5 又补了一句：`33-gate-registry.json` 的键名、id、status、事件锚、事件成员不动。

这两句现在都改了。§R10-3 只留「出仓的机器读名字一律不动」，§R10-5 把键名能不能改交给本文件判。机器名怎么分类、哪类能改，一律按本文件第 1 条，不再按「一律不动」判。

另外两处常被当成这条规矩的出处，实际不是：

- `docs/adr/0028-current-architecture-and-docs-authority.md` 的 Consequences 里有一句「这次改动不改变……任何机器读的名字、字段、命令、错误码、文件路径和插件身份」。那是在说 0028 自己那次改动做了什么，不是面向以后的禁令。
- `engine/test/contracts/87-check.mjs` 开头写着「防字段改名后守卫空转」。这句是 87-check E 组的设计说明（要求 `guards[]`、`confirmations[]` 两族各有引用），不是禁令本身。

`docs/authority.md` 没有这条规矩的正文，它只记「决定和术语分别写在哪」。

这条规矩当初立得住：报告 JSON 的键、数据库的列，仓外的脚本和报表在读。名字一改，那些读者当场就挂，而且挂在他们那边，本仓的检查看不出问题。

卡住的地方是画得太宽。要动 `33-gate-registry.json` 这种只在本仓被读的字段键名，也被一并挡住。这类名字的读者全在本仓，改名时能把读的地方一起改完，没有「外面的人会挂」这个风险。要放宽的是宽度，不是「名字随便改」。

## Decision

### 1. 哪些名字能改：按「谁在读」分三类

判据只有一句：改掉这个名字，出了本仓，还有谁读它？

- **出仓的名字，不准改。** 报告 JSON 的键、数据库列、错误码、命令行参数、环境变量、`preview_disclosure` 及其下的字段、文件路径、插件身份。仓外有读者，改名等于替别人做决定。
  这条线按「会不会随产物发出去」判，不按「文件在不在仓里」判。一个字段的源码在 `engine/src` 里，但它的值被写进 `--out` 给了用户的 `audit-measurements.json`，那它就是出仓的名字。
  已查实的例子：`engine/src/audit/upstream-dimension-map.ts` 里的 `map_review`（含 `last_reviewed` / `next_review`）会被写进 `measurements.upstream_dimension_projection`（调用点 `engine/src/audit/audit.ts`），再落成 `audit-measurements.json`。这两个字段因此算出仓，钉死在这里；以后要动，先补「仓外读者清单」。
- **只在本仓里被读的名字，可以改。** 现在这类只有一个实打实的例子：`33-gate-registry.json` 的字段键名。条件是第 3 条：同一笔改动把读它的脚本、登记表和文档一起改到全绿。
- **当时留下的存档，不追改。** `examples/first-report` 四件、`38-*` 那组按字节冻住的存档、`48-micro-a-golden-*` 十二件、`23-frozen-*` 那几件（bundle 和 readme 覆盖件）。`23-gates.json` 也按历史读，但它不属于按字节冻住那一类，见下一段。
  `23-gates.json` 能被 `engine/test/contracts/23-first-report.mjs` 整份重写，golden-ci 也只逐字节比 `examples/first-report` 那四件，没有谁盯着它。所以它只是「当时留下的记录」，靠约定不动，不是机器钉死的。里面是首报当时的计数，改键名会让首报的数字对不上来源；所以照样按历史读、不追改。

三类不重叠。一个名字同时被仓外和本仓读，按出仓算；一个名字既在真会被读的登记表里又被抄进存档，登记表那半边按第二类、存档那半边按第三类。

`docs/spec.md` §R10-4 说的是英文文书的写法（「机器名原样」），它管的是英文段落里不要自己翻译机器名，不归这条规矩管；本 ADR 不改那一句。

### 2. 怎么过渡：只在本仓读的一次全改，出仓的要动就并存

- **只在本仓读的：同一笔改动全改，不留并存期。** 读它的脚本都在本仓，一次改完就能一起变绿。留一份旧键没人用，下一轮读的人还得猜哪份算数。
- **出仓的真要改，走三步。** 第一步加新名，报告 schema 版本号跟着加一档，旧解析器继续认旧名。第二步两套名字并存放一个版本，让外面的读者换过来。第三步删旧名。删旧名单独开票，不许在第一步里顺手删。
- **没有「仓外读者清单」不许改动出仓的名字。** 谁在读，先写清楚；写不出来就说明还没到能动的时候。

本文件已是现行，只放宽第二类。出仓的名字维持原样。

### 3. 改了以后哪些检查要跟着动

按现在的写法，读 `33-gate-registry.json` 字段的地方是这些：

- `engine/test/contracts/87-check.mjs` A1 读 `meta.reference_resolution`；E 组读 `items[].guards`、`items[].confirmations[].evidence` 和 `confirmations[].reason`。
- `engine/test/contracts/48-check.mjs` E1、E2、E3 读 `events[].occurred`、`events[].evidence`、`items[].id`、`items[].status`、`confirmations[].decision`、`confirmations[].by`。
- `engine/test/contracts/45-check.mjs` H8 读 `items[].id`、`items[].status`、`items[].decision`。
- `engine/test/contracts/50-check.mjs` E1 读 `events[].occurred`。
- `engine/test/contracts/51-check.mjs` F1 读 `items[].id`、`items[].confirmations[].decision`。
- `engine/test/contracts/72-check.mjs` C2 读 `events[].occurred`。

工单点名的五项里，`87`、`48`、`51`、`72` 这四条在上面。`71-check` 不读这份登记表：它读的是 `engine/src/audit/upstream-dimension-map.ts` 和 `docs/upstream-dimension-map.md` 里的 `last_reviewed` / `next_review`。这一对在第 1 条已经划成「出仓、不许改」，所以它虽然按字段名读，这轮不动它。

`44-check` A16 也按字面钉住了这两个字段名，外加 `进入条件`、`永久排除`、`S5 ↔ S4` 这些字样。两个字段名属于出仓那一类；其余是文档里的固定说法。都不在本轮改动范围。

`45`、`50` 不在工单点名的五项里，是顺着查出来的。

文档面同批改了：`docs/spec.md` §R10-5 与 §R10-7 改成指向本文件（§R10-3 的禁令那句收窄成「出仓的机器读名字一律不动」并加链接）、覆盖表一行；`docs/authority.md` 顶段、§2 表里 `engine/test/fixtures/contracts/` 那一行、§4 那条。`docs/adr/0028-*.md` 只有 Consequences 里那句「机器读的名字」还按原样留着——它说的就是 0028 自己那次改动，跟本文件不冲突，不动。

改的顺序：数据和脚本一起改，同一笔提交，跑绿为准。不许先改数据后改脚本，也不许反过来。中间那一刻两边对不上，检查会红，红的原因还看不出是谁的错。

改完之后谁来拦——分两种情况，别一概说成「都会红」：

- **删掉整段或整族会被拦。** 比如 `items[]` 没了，或 `events[].occurred` 改名，50-check E1、72-check C2 读到 `undefined` 会直接判红。
- **只改一个字段名，不一定红。** `87-check` E2 把 `confirmations[].evidence` 和 `confirmations[].reason` 合并抽取后只做整表汇总，旧键读出 `undefined` 会被 `filter(Boolean)` 悄悄丢掉；只要同一条的另一半、或别的条目里还有能解析的引用，E2 就照样通过。这类改名机器拦不住。

所以真正的防线是两样：同一笔提交把读的地方改全，加人审。`87-check` 没有逐条校验 `evidence`、`reason` 是否各自非空，这一点如实记在这里，别指望它。

**另外拦不住的一种**：把字段换成另一个「存在但意思不同」的字段，检查也不会红。同样是靠人审。这是放宽换来的代价，不许以后当成没发生。

### 4. 老报告和老事实表怎么办

- **默认按历史读，不追改。** 当时留下的存档照旧：按字节冻住的存档一个字节不动，读的时候按当时的样子读。
- **出仓的名字真走到改名时，老数据库按旧列名只读。** 不跑 `ALTER TABLE ... RENAME`：只追加守卫把 `ALTER` 拉黑了，改名等于改写历史行，正好撞在这条守卫上。
- **真要统一口径，走「新建表 + 重算 + 以新观测集追加」。** 旧库留着不动，新产物算新的一次观测集，不覆盖旧集。
- **重算只在明确要求时做。** 平时不为了「好看」重算历史。

### 5. 87-check 开头那句怎么办

不动。它现在说的还是「防字段改名后守卫空转」，本 ADR 生效后它的意思变成：改名时消费面必须跟着改，而且改完仍然有引用可查。E 组要求 `guards[]`、`confirmations[]` 两族各有引用这件事不变。

### 6. 本 ADR 不做的事

- 不改任何键名、不改任何检查脚本、不改任何已经冻住的存档。
- 不放宽出仓的那一类，不加新的「并存期」例外。
- 不新增编号体系，不动 `docs/authority.md` §3 的历史号政策。
- 改键名的实现票另开；tracker #212 那张只写决定，不做改名。

## Considered Options

- **一次全改，出仓和仓内的名字一起动**：报告 JSON 键和数据库列一改，仓外读者当场挂；而且老库的 `ALTER` 被只追加守卫拉黑，改列名等于改历史。这条路还没开始就得停机。
- **只留一句口号，不给判据**：规矩变成「看情况」。下一笔改动谁也说不准自己算不算越线，最后还是要回来开会。
- **只在本仓读的也要求并存期**：读它的脚本全在本仓，同一笔改动能一起改完；并存期只会留下没人读的旧键，下一个人还得查哪份算数。
- **一直不改，等真有需要再说**：现在就有需要。白话收尾已经把说明文字清完，剩下卡住的就是键名这一层；等着等于把这件事无限往后推。

## Consequences

- 本文件是现行决定，仓里因此有两类「机器名」：出仓的（仍不许改）和只在本仓读的（同一笔改动可以改）。读文档的人要先看清问的是哪类；一句「机器名不许改」已经说不全了。
- 只在本仓读的一改，至少六条读登记表的脚本要动（第 3 条那份清单），是同一笔改动的一部分，不是额外工作。漏改不一定被检查发现：删掉整段或整族会当场红，只改一个字段名则可能照样绿（第 3 条写明的原因）。所以别拿绿灯当改名完整的凭证，同一笔提交改全加人审才算数。
- 出仓的名字若真走到并存期：那段时间两套名字都得能读，维护旧解析器的责任归提议改名的那张票，期限就是那个并存版本。并存期结束、旧名删掉之前，谁都不许停下来。
- 剩下的缺口（同形不同义拦不住）已经在第 3 条写明，只能靠人审。
- 本 ADR 现在是现行，够资格当 `Design:` 指针的目标。
- `engine/test/contracts/docs-authority-check.mjs` 的头注释和 C0 标题还写着「现行 ADR 只有 0028」，接受本文件之后这话就过期了。改那处口径的活单独在 tracker #230 里做，本票不动检查脚本；在那之前脚本照旧全绿，因为它只核 0028 恰有一份、历史号没复活，不数现行 ADR 有几份。
- 当时留下的存档不追改这一条把历史报告保住了：老报告还在，按当时的样子读，不会因为以后的改名失效。
- 这次改动不动产品功能，不改任何键名，不改任何检查逻辑。
