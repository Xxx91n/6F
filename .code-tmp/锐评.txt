### 1. 致命命门：“跨环境逐字节确定性”的神话，被 Git 2.45 的时区格式直接击穿

- **精确代码来源**：
  - `engine/src/demo/demo.ts` 第 160 行：
    ```typescript
    const HEAD_DATE = git(repoDir, ['log', '-1', '--format=%cI']);
    ```
  - `engine/src/demo/demo.ts` 第 165 行：
    ```typescript
    traceId: sha256Hex(def.repo.name + '|' + HEAD_SHA + '|' + HEAD_DATE).slice(0, 32),
    ```
  - `engine/test/demo.test.mjs` 第 100-104 行（实跑断言）：
    ```javascript
    check('O2 实跑产物与 golden 逐字节一致（report.md/report.json/facts/measurements）', ...);
    ```
  - `.github/workflows/golden-ci.yml` 第 10-18 行（平台裁定声明）。

- **锐评剖析**：
  你将 Demo 生成物与 Golden 资产做逐字节比对（`O2` 和 `O3` 断言），并信誓旦旦在 `golden-ci.yml` 里写道：“*重渲染确定性是逐字节级契约而非平台行为……单平台跑即可，不挂 3 平台矩阵*”。
  然而，你获取时间戳使用的是 `git log -1 --format=%cI`。
  **在 Git < 2.45（如 Debian 12 默认 Git 2.39）中，UTC 时区的 `%cI` 输出为 `2026-04-13T10:00:00+00:00`；而 Git ≥ 2.45（GitHub Actions Ubuntu 24.04 runner）将其严格对齐为 `2026-04-13T10:00:00Z`。**
  就因为这个 `+00:00` 与 `Z` 的差异：
  - `HEAD_DATE` 变了；
  - 基于 `HEAD_DATE` 派生的 `traceId` 变了；
  - DuckDB 里的每一个 `fact_id` 全变了；
  - 最终的 `RCP`（Receipt ID）和全量生成的 `report.md`、`report.json` 全部哈希漂移！
  在当前机器上只要运行 `npm test`，`demo.test.mjs` 会立刻发生 `FAIL O2` 和 `FAIL O3`。你耗费无数心力构建的“跨环境绝对确定性”，被底层宿主环境一个几行代码的 Git 升级无情碾碎。

### 4. 文本文字狱：纯字符串匹配搞出的“只追加（Append-Only）守卫”

- **精确代码来源**：
  - `engine/src/fact/schema.ts` 第 47-75 行：
    ```typescript
    export const REWRITE_BLACKLIST: readonly string[] = [
      'UPDATE', 'DELETE', 'DROP', 'ALTER', 'TRUNCATE',
      'INSERT OR REPLACE', 'ON CONFLICT DO UPDATE', 'MERGE INTO', 'COPY'
    ];

    export function classifyStatement(sql: string): StatementVerdict {
      const s = normalizeSql(sql);
      if (s.length === 0) { return { allow: false, reason: 'empty statement' }; }
      for (const bad of REWRITE_BLACKLIST) {
        if (s.includes(bad)) { return { allow: false, reason: 'rewrite form rejected: ' + bad }; }
      }
      for (const good of STATEMENT_ALLOWLIST) {
        if (s.startsWith(good)) { return { allow: true, reason: 'allowlisted: ' + good }; }
      }
      return { allow: false, reason: 'default deny: not in allowlist' };
    }
    ```

- **锐评剖析**：
  在 ADR-0005 和 ADR-0019 中，你大谈 DuckDB 单写多读（SWMR）、事件溯源（Event Sourcing）、底层不可改只追加机制。
  结果到了代码落地层，你的实现居然是拿 SQL 字符串做 `s.includes(bad)`！
  它甚至不是一个 SQL Lexer！这意味着只要用户执行这样一条合法只读查询：
  ```sql
  SELECT * FROM audit_fact WHERE metric = 'UPDATE';
  ```
  或者查询内容中包含了字面量 `'DROP'`，你的白名单守卫就会立刻尖叫并抛出 `AppendOnlyViolation: rewrite form rejected: UPDATE`！这种把 SQL AST 治理降维成低级敏感词过滤的做法，粗糙得令人发笑。

  - `engine/src/report/narrative.ts` 第 56-65 行（`BAND_PATTERNS` 正则屏蔽）：

### 7. 一次性克隆陷阱：永远不会拉取新代码的 Repo Intake

- **精确代码来源**：
  - `engine/src/intake/intake.ts` 第 111-125 行：
    ```typescript
    export function cloneToIsolatedCache(url: string, cacheRoot: string, timeoutMs = 600000): CloneResult {
      const key = sha256Short(url);
      const dir = join(cacheRoot, 'repos', key);
      if (existsSync(dir)) {
        if (isGitRepo(dir, 30000) && remoteOriginUrl(dir, 30000) === url) {
          const shallow = isShallowRepo(dir, 30000);
          if (shallow) { throw intakeError('SHALLOW-CLONE-REJECTED', 'cached clone is shallow: ' + dir); }
          return { dir: dir, cloned: false, head_sha: headSha(dir, 30000), shallow: false };
        }
        throw intakeError('INTAKE-CACHE-COLLISION', 'cache slot occupied by foreign content: ' + dir);
      }
      ...
    ```

- **锐评剖析**：
  你为远程 URL 仓库接入设计了详尽的隔离缓存（`sha256(url)[:16]`）、禁用钩子、禁止浅 clone。
  但在缓存命中逻辑上：**只要目录存在且 remote URL 匹配，它就直接返回已有的 `headSha`，根本不执行 `git fetch` 或 `git pull`！**
  这意味着同一个远程仓库如果有了新的 commit，你的系统将永久视而不见，永远停留在第一次 clone 时的快照里。
  而且，如果用户第一次输入带 `.git`，第二次没带，两者的 sha256 键不同还可能直接踩入未定义的缓存状态甚至报冲突。

### 9. 考古奇观：为了在 CI 证明“确定性”，把未提交的 Bundle 塞进 Git

- **精确代码来源**：
  - `.github/workflows/golden-ci.yml` 第 40-60 行：
    ```yaml
    # ---------- Leg 2：examples/first-report 重渲染 + 逐字节 diff ----------
    # 重生成命令（examples/first-report/README.md 所录，逐字）：
    #   node .scratch/architecture-recovery/reports/23-first-report.mjs
    # 脚本审计 HEAD，须在工作树处于生成 commit fc00d458 的状态下运行方可复现。
    # fc00d458 是 GitButler workspace 快照（不在任何 pushed ref 上），经仓内 bundle
    # 23-frozen-fc00d458.bundle 传输（前置对象 200b344 在 main 历史中）。
    # 其树外还需生成时点未入库的三件（随 e39468c 入库）：
    #   23-first-report.mjs / engine/src/report/generate.ts / .scratch README
    # 其中原脏 README 已失——23-frozen-readme-overlay.md 为等签名重构
    # （经 23-facts.jsonl 逐 keyword intent_count 复原 top-20 签名，实测四件逐字节一致）。
    - name: materialize frozen worktree (fc00d458 via in-repo bundle)
      run: |
        git bundle unbundle .scratch/architecture-recovery/reports/23-frozen-fc00d458.bundle
        git worktree add .frozen-first-report fc00d458e215cc9a7a26af81626dec8712622821
        mkdir -p .frozen-first-report/engine/src/report
        git show e39468c9c53d32694f2ef9153b79eae018ea6b44:engine/src/report/generate.ts > .frozen-first-report/engine/src/report/generate.ts
        git show e39468c9c53d32694f2ef9153b79eae018ea6b44:.scratch/architecture-recovery/reports/23-first-report.mjs > .frozen-first-report/.scratch/architecture-recovery/reports/23-first-report.mjs
        cp .scratch/architecture-recovery/reports/23-frozen-readme-overlay.md .frozen-first-report/.scratch/architecture-recovery/README.md
    ```
  - `.scratch/architecture-recovery/reports/` 目录下直接提交的多个 2MB+ 二进制 DuckDB 文件（`38-audit-facts.duckdb`, `39-audit-facts.duckdb`, `51-audit-facts.duckdb`）。

- **锐评剖析**：
  **这是整个项目中最令人叹为观止的“工程形式主义闭环”：**
  当时为了跑出首份真实报告（`23-first-report`），工作区是脏的，依赖了一个临时未提交的 GitButler 快照（`fc00d458`），而且当时的某个脏 `README.md` 还丢了。
  正常的工程做法是：认同这次历史运行不可复现，重新基于 clean commit 跑一份新的 baseline。
  但你的做法堪称惊世骇俗：
  1. 把未推送的 GitButler 快照打包成 git bundle 二进制（`23-frozen-fc00d458.bundle`）塞进仓库；
  2. 根据旧日志里的关键词命中数，反向捏造了一个“等签名重构”的 README 覆盖层（`23-frozen-readme-overlay.md`）；
  3. 在 CI 运行阶段，用 `git bundle unbundle` 恢复分支，用 `git worktree add` 挂出临时目录，强行拷贝覆盖文件，只为了让 CI 跑出与历史首报逐字节一致的比较！
  为了圆一个“逐字节确定性”的谎，搭上了一整座中世纪发条钟表般的复杂脚手架。更别说仓库根目录还提交了十多兆的 DuckDB 二进制数据库，完全击穿了现代 Git 仓库不存大型二进制中间产物的基本常识。

## 💡 总结与建议：给作者的一剂解药

你展现了极强的架构拆解能力、高超的文档撰写素养以及对领域建模（Domain Modeling）和安全边界（如 hooks 隔离、凭据不落地）的深刻理解。这套架构如果在正规军的航天级或金融级审计系统里，是一套极具前瞻性的蓝图。

但对于一个工程工具而言，当前项目患上了严重的**“形式主义与架构通胀并发症”**：
1. **停止沉迷文书治理循环**：不要在 `.scratch/` 下无休止地写下一轮交接任务书、审核上一轮审计报告的勘误表了。

3. **连通孤岛适配器**：把写了 1200 多行却完全架空的 `codelore.ts` 与 `github-rest.ts` 真正接进数据流中。
4. **解绑虚假的“逐字节确定性”**：时间戳与平台差异是客观存在的物理规律，放弃脆弱的字符串/字节级 diff，拥抱结构化语义比对（Semantic / AST Diff）；修正对 Git ISO 8601 时区（`+00:00` vs `Z`）的处理，让测试套件在任何标准 Linux 机器上都能稳定通过。
