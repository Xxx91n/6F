# R50-Q2 调研题面 —— 开工「任务书声称态 vs commit 史实证」对表入闸

（提交 atomcode-research 深调研；账本=唯一事实源立场，调研须回顾 decision-ledger 全部 current 记录、docs/adr、CONTEXT.md 词条、工业界成熟落地心智模型为重点。）

## 背景

本仓=五尺度工程内容审计产品的 spec-level 规划+治理仓。工作流采用任务书驱动制：grill 轮产出常驻任务书（.scratch/macro-audit/handoffs/next-round.md），执行批按任务书施工。开工已有三件套建制（必读要点/覆盖 ID/验收标准原文）＋开工闸门=DoR（依赖闭合即可拉）。

轮50 实证事件：任务书载 T1-D「F3/F4 未实施」（生成时点为真），而 git log 显示轮49 LOOP 审计修复批已以包C/包D 预声明落地（commit c6cb5a33/36e4d264）——任务书生成后 LOOP 先行落地致书失真。执行批开工核对自行发现差异、按剩余义务裁剪（等价性自证件＋普查＋守卫收口），避免了重复实施/双重修复 commit。即：本轮是被执行者自发 diligence 接住，非建制兜底——若漏接，照书施工将产生重复实施污染 commit 史（轻则空跑重则双重修复引入 diff）。

根因=任务书生成时点与实际状态的时序缝——书生成后世界继续动（LOOP 落地、他分支进展、上游漂移），任何「声称态」都可能在开工时已失真。同类风险面：任务书声称「未注册」「未修」「待裁定」等状态性断言均可能跨窗失真。

## 候选

(i) 入闸立法：开工三件套加第四条——「任务书声称状态对表：凡任务书声称『未实施/待做』的源码面义务，开工时须 git log/show 实证核实；发现已落地→登记差异行并按剩余义务裁剪，不得照书施工」。利=建制兜底不依赖执行者自发细心＋成本≈一条 git 命令；弊=工序+1 行。
(ii) 文书面修：任务书换代模板加自检注记——换代时对「未实施」条目核对在史 commit 再落笔。利=从源头治失真；弊=只管换代时点，挡不住「换代后又被 LOOP 落地」的时序缝（本轮正是此类）。
(iii) 不立规：本轮个案——任务书换代与 LOOP 落地撞同窗属小概率，且本轮已被接住零害。利=零新规；弊=再发=重复实施/双重修复 commit 风险裸露。
(倾向 (i)＋(ii) 双侧：闸侧兜底＋书侧降发生率，成本均≈零。)

1. 工业界成熟心智模型（重点）：工单/issue 驱动施工中「工单声称态 vs 代码现实」失真的治理惯例——开工前 verify-before-work 惯例（如「先复现 bug 再修」纪律、XAUI/栈检 pre-flight checklist）；并行施工中工单过期（stale work order）防护模式；敏捷/Kanban 中「卡片状态滞后」处置惯例；repair shop/运维工单系统的「开工前资产状态核验」心智；DB/分布式系统乐观并发控制的「读后写前重验」同构（task 书=读快照、施工=写、对表=重验）；重构工具/IDE 的「应用前基准校验」（precondition revalidation）先例；重复工作防御（idempotency/at-least-once 语义下的 dedup 心智）；审计/合规域「文件记录与实物状态对账」（inventory reconciliation）惯例。
