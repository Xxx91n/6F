# R30-Q4 atomcode 深调研报告：文件级事实存储 grain（A/B/C/D）

> 运行：2026-09-23（atomcode -p，session bf48f297）；题面见 R30-Q4-research-prompt.md。
> 置信度=高（主干 4+ 独立信源交叉）；引擎实况=Tavily 缺位，Exa/AnySearch+web_search+知识库沉淀混合。

## 1) 执行摘要（Tl;dr）

**推荐 B：采集时逐 path 发射 subject_ref=<file> 一等事实，现有 facet_rows 聚合载荷降格为 raw 证据层（raw+normalized 双层）。** 理由：工业界四类产品（SonarQube、CodeScene、Sourcegraph SCIP、CAST）无一例外以 per-entity 行为一等存储 grain——SonarQube schema 是直接同构权威（COMPONENTS 表 QUALIFIER=FIL 逐文件行＋MEASURES 表 per-component JSON 载荷）；append-only+fact_id 哈希+provenance 与 medallion「bronze 保 raw＋silver 保规范化事实」审计证据保留惯例完全同型。A 在工业界无先例（没有一家成熟产品把全仓逐 path 数据塞进单行再靠查询切片）；C 撞 dual-write 反模式；D 制造「同一事实两阶段身份」问题比 B 更复杂且收益不明。

## 2) 对比矩阵（候选评估）

| 候选 | 工业界先例 | SSOT 契合度 | 主要风险 | 判定 |
|---|---|---|---|---|
| A 查询时按 path 过滤聚合载荷 | **无先例**——业界只做「聚合表 atop detail fact」（反向） | 差：subject=面非文件，fact_id 落在面上，文件变更粒度粗，append-only 去重失效 | 文件不成一等 subject→卡/MCP/跨尺度关联全要解析巨型 JSON；一行变更=全仓行数组重写哈希；provenance 仅行定位符追踪断链 | ❌ |
| B 逐 path 一等事实＋facet_rows 转 raw 层 | **强先例**：SonarQube COMPONENTS FIL+MEASURES；SCIP per-document symbol；CodeScene file level 一等；CAST per-file | 好：fact_id=subject 粒度哈希去重精确到文件；聚合面降 raw 证据与 bronze「保真+可重建」同型 | 采集端改发射粒度；行数×N（DuckDB 列存 append 友好） | ✅ **推荐** |
| C 聚合+per-file 双写并存 | 反模式：Auth0 dual-write+事件溯源复盘一致性噩梦 | 差：两个「一等事实」无 SSOT 边界 | 双事实源→消费方选权威→隐蔽 A/B 混用 | ❌ |
| D lazy 升格 | 近似先例=SCIP incremental indexing——但那是采集调度优化非存储 grain 延迟决策 | 中：fact 身份两阶段，fact_id 语义漂移 | 同指标同文件两种 grain 并存；升格写回与 append-only 审计语义冲突（事后补写改变「采集时点」证据属性） | ⚠️ 仅作采集调度非 grain 决策 |

## 3) 分点结论

1. **SonarQube=最直接同构权威**：schema-sq.ddl（官方 SCM autogenerated）COMPONENTS 表每行一组件（QUALIFIER=FIL=文件行）；MEASURES grain=per component per branch，JSON_VALUE CLOB 存全部指标+JSON_VALUE_HASH 变更检测。演进方向=「subject 一等行+值 JSON 化」=本仓 fact_id=subjectRef+metric+valueJson 设计的镜像。**载荷可 JSON 化，但 subject 边界必须是文件级行**——A/B 分水岭；
2. **CodeScene**：file/architecture/function 三层 hotspot 均一等分析对象（「同一指标在多 subject 粒度上各有一等事实」非「聚合载荷+查询切片」）；
3. **Sourcegraph SCIP**：per-document/per-symbol 事实是索引 grain，使能 incremental indexing+跨语言导航（Glean 集成者评 SCIP「8x smaller, 3x faster」=符号级事实行红利）→**subject 一等化使能增量补采/跨尺度关联/精确历史追踪**；
4. **Medallion 分层=审计类系统标准双层**：Databricks 官方档 bronze「preserves fidelity/enables reprocessing and auditing」、silver「validated non-aggregated representation」、聚合放 gold。映射：**facet_rows 聚合载荷=codelore 原始输出=bronze/raw 证据层（append-only 保留供重建+审计）；逐 path normalized fact=silver 一等审计事实；仓级报告=gold 读模型**——与知识库 Kimball 沉淀互证（quarantined/normalized 同事件流，处置是属性非种类）；
5. **C 双写治理教训**：Auth0 dual-write+生产事件溯源复盘——任一写失败留不一致态，补救（outbox/重放/版本检测）全是「不得不用双写」的代价；CQRS 正确形态=SSOT→派生投影单向（投影是 facts 另一种解释可 truncate+replay 重建）——C 让两形态同为一等事实=消费方失裁决依据；
6. **查询时切片 vs 预物化判据**（MotherDuck 官方指南五变量=数据变化频率/查询模式/规模/SLA/运维）：文件卡的切片维度（单 path×多指标）是采集时不可预知的交互式查询→**应物化 detail-level fact（逐 path 行），聚合报告反而是已知可重算投影→不必持久化为一等事实**——Kimball 判据标准答案：先定 detail grain，aggregate 是其上可选优化层非事实源；
7. **provenance**：per-file fact 行自带 subjectRef+observedAt+valueJson 哈希=可独立引用证据单元；A 的「面级 fact_ref+行定位符」是弱引用——行定位符（JSON 数组内 path 下标）随载荷 schema 演进脆弱；B 的每文件事实有稳定 fact_id，MCP 只读接口可直接按 fact_id 引用；
8. **D 的唯一合理形态=采集调度非存储决策**：SCIP incremental indexing=按需只索引变更文件，但被索引文件产出的一等事实 grain 从一开始就是符号级。本仓「首查 lazy 补采」（D-122③ 已定）应实现为：CLI 首查→触发补跑→**发射与批量采集完全同构的 per-file 事实（同 grain 同 fact_id 规则）**——存储层永远只有一种 grain，lazy 只是发射时机（置信中，逻辑推演）。

## 4) 对现有设计的具体映射建议

- audit_fact（normalized/silver 层）：grain=逐 path×逐指标×observedAt，subject_ref=<file path>，value_json=该文件该指标的标量/小对象（对标 SonarQube MEASURES per-component JSON）；
- facet_rows（raw/bronze 证据层）：保留 codelore 原始聚合输出 append-only，标记 role=raw_evidence，不参与文件卡查询主路径，仅供重建/争议仲裁/面级历史对照；
- 仓级报告=gold 投影（可重算读模型），不新增事实表；
- lazy 补采走与批量相同的发射管线，grain 无二义。
